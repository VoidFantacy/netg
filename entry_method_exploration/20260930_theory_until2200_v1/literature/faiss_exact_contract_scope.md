# 精确标签、浮点身份与批处理费用

2026-09-30核对Faiss官方资料。这里讨论实现合同，不把工程配置称为新的检索方法。

[官方Implementation notes](https://github.com/facebookresearch/faiss/wiki/Implementation-notes)现在按 `nq*d < 128000` 描述直接距离与BLAS分派，页面主体是L2。[FAQ](https://github.com/facebookresearch/faiss/wiki/FAQ)仍含旧的“batch大于20”说明，并解释浮点求和、并列和批处理效率。不能把FAQ旧阈值直接当作本地1.15.0、raw-IP的执行依据。本次IP分支判断来自[固定tag距离源码](https://github.com/facebookresearch/faiss/blob/v1.15.0/faiss/utils/distances.cpp)与本地运行时参数；也没有把L2展开式中的消去误差直接归因给IP。

数学上的全库top100前十名与top10相同，需要相同的全序（包括并列规则）。实际接口的“exact”指全库评分，未承诺更改BLAS调用形状、结果容器或返回k后仍逐位恢复原输出。因此应分别检查：

1. 被下游消费的有序ID、ID集合与距离bits；近似数值相等不等于ID身份。
2. 保留的ID是否处于独立float64全库边界附近；数值容差只用于排除明显实现错误，不能将其写为严格排序一致。
3. 完整构建的H、温度、权重、W和小图。即使1024条完全相同，也不能证明另外18976条和最后短批相同。

固定预算少标注可以降低GT调用数；它仍可能增加教师、选样和第二次base载入。共享工程优化必须同样用于完整标签参照；完整费用要重新测量。索引加载、输出、启动和核验的边界分别记录，不把8线程离线标签吞吐称作单线程ANN QPS。

若后续为保存预算只写真正消费的前缀，应在新协议中预先约定，对双方统一执行、保留全返回hash及验证证据，并承认输出费用合同变化。不能在旧费用报告里暗中缩短结果文件，也不能删除旧文件以腾挪预算。

[The Faiss Library v4](https://arxiv.org/html/2401.08281v4) §3.1把距离计算与top-k维护分开讨论，包含直接计算/矩阵乘和heap/reservoir；§3.2–3.3把构建费用列为受应用场景影响的资源指标。附录A.3强调优化前后的正确性对照与批处理。论文未承诺任意数据形状均更快，也不支持从本微测外推冷缓存或完整构建。该文§3.2还区分1-recall@k和k-recall@k；本项目继续使用真实R1与R100交集定义。
